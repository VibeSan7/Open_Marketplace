# Isolated demonstration order journey

Owner requests a verified project on GitHub without more ordinary technical questions. This is a demonstrator, NOT production financial infrastructure. General specification sections 16–17 remain gates for real commerce.

## Product and safety decisions

- New Django app `demo_orders`; URLs `/demo-orders/`. Every page and every order says «Тестовый заказ — реальные деньги не списываются». No card/password collection, payment API, SMTP changes, external calls, shipping addresses or real dispatch.
- `DEMO_ORDERS_ENABLED` defaults false, enabled only by the exact environment string `true`. Disabled HTTP endpoints return 404; public application functions also reject writes when disabled. Tests override this setting explicitly.
- One order contains one selected physical offer/variant from one seller. Shared cards link to concrete offers; never silently choose a different seller. Buyers must be live, admitted ordinary accounts. Existing catalogue/session/seller authorization remains unchanged. A seller cannot buy their own offer.
- Capture immutable published title/variant, seller display name, unit, unit price, quantity and total at checkout. Server calculates totals using Decimal; round quantity × unit price to two RUB places with ROUND_HALF_UP. No external delivery; UI explains simulated pickup, additional charge 0. No claims about real fees/taxes/delivery.
- Use SEPARATE `DemoInventory` balances per physical variant: initialize once from the sum of known positive catalogue Stock quantities when first ordering. Do not change Product/Variant/Stock, admission or seller tables. Catalogue quantities are never returned to buyer pages; show only simulated remaining quantity with a prominent label. Later real stock edits do not reset/replenish simulation. This frozen simulation is documented; it is not real reservation or oversell protection for commerce. Exact simulated quantities are shown only to the owning seller, never the buyer, because initialization copies private stock. Buyers only receive their ordered quantity and transition state.
- Consistent initialization/locking: read-lock the physical Variant row (without mutation) before creating/locking its DemoInventory, then atomically re-read the fresh public offer/price and reserve simulated quantity. Serialize same-buyer idempotency using an appropriate stable account row lock or unique intent receipt; no silent IntegrityError leak.
- Require client-generated UUID `intent_id` on create, unique per buyer. Replay same intent with identical offer/quantity returns same order, never deducts twice; changing the payload with same intent gives conflict. Reject noncanonical UUID, unknown/duplicate POST fields and non-finite/negative/zero/excess-precision quantities. Use existing stock_value for unit precision. Monetary database capacity must fit supported unit-price × quantity inputs or reject overflow at the boundary.
- State machine: `pending` → `paid` → `handed_over` → `completed`; `pending`/`paid` → `cancelled`. All labels explicitly simulated. Buyer selects simulate-success or simulate-decline: decline leaves pending and permits later success. Seller alone marks handed_over; buyer alone marks completed. Buyer or owning active seller may cancel before handover. Cancel paid records a simulated refund status, never a real refund. Terminal repetition is idempotent; invalid transitions conflict. Cancellation returns simulated inventory exactly once. No expiry scheduler or guessed production reserve periods: simulation reserve lasts until explicit cancellation.
- The buyer and actual owning seller alone can read an order; all other accounts including unrelated service accounts get identical unknown/foreign denial without data leakage. Revalidate live session, admission and active seller status on relevant actions. No shared-header CSRF form; POST actions have CSRF protection. Error responses contain no random CSRF markup. GET is read-only.
- Store append-only order events (state/action, actor UUID, timestamp) with no email/password/sensitive data; reads return no internal/session identifiers. Keep application API in `demo_orders/public.py`, views in `demo_orders/views.py`, Russian templates under `templates/demo_orders/`.

## Integration contract

Routes: `demo-orders` list, `demo-order-create` at `new/<uuid:variant_id>/` GET preview+POST intent/quantity creation, `demo-order-detail` at `<uuid:order_id>/`, `demo-order-action` at `<uuid:order_id>/action/` POST explicit action. Named routes un-namespaced like existing web modules.
Expose public `create_order(variant_id, quantity, intent_id, context)`, `get_order(order_id, context)`, `list_orders(context)`, `act_on_order(order_id, action, context)` (keyword-only). Returned DTOs must support templates and immutable snapshot assertions, never ORM objects to templates.
Read-only dependencies on catalogue models are explicitly confined to a single offer-snapshot helper in this isolated test demonstrator; catalogue writes are prohibited. Existing production modules must not import demo_orders except root app/URL wiring and optional links. No dependencies or new tools required.
