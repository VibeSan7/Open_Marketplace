# Marketplace storefront v0.4

## Authorization and product boundary

The owner selected Wildberries and Ozon as familiar marketplace references and approved the proposed storefront, public browsing, rich synthetic catalog, cart and connected order journey. The owner delegated ordinary choices and asked for the finished result, not another interview. This specification records those choices before implementation. Brand identity, content and assets remain original; this is not a claim of parity with either reference service.

The deliverable is the existing Django application, tested, published in the existing repository, and installed in the authorized local demonstration with backup and rollback. No real payments, shipping provider, production deployment, external credentials, new copyright licence or paid service is authorized. Demonstration transactions remain explicitly labelled and controlled by DEMO_ORDERS_ENABLED.

## Locked design decisions

- Primary surface: Explore. Product photography, search, category shortcuts and a responsive product grid dominate. Do not use the old instruction page as the home. Use a restrained teal accent, near-white canvas, charcoal type and warm category surfaces; keep the Open Marketplace name. No copied trademarks, invented reviews, fake crossed-out prices, popularity or delivery promises.
- Common header: home/brand, catalog, search, favorites, cart, orders and account. Separate seller/setup/staff navigation from buyer shopping. Mobile controls have at least 44px targets; no horizontal overflow at 390px.
- Home displays only explicitly public eligible products even for logged-in members. Catalog/detail/seller/photo GET routes are browseable anonymously but must enforce the same visibility rule at the data boundary. Counts, facets, suggestions, offer links, prices, sellers and photographs must not disclose private products.
- Add Product.public_listing, default False. The migration does not opt existing records in. Public listing is an explicit owner/authorized-manager action protected by session, CSRF, ownership and transaction checks. It never publishes drafts or overrides blocking, seller suspension, category inactivity, withdrawn variants or photo ownership. Old admitted participants retain their existing private catalog access; public opt-out immediately removes anonymous visibility.
- Active, email-verified ordinary users can save and order eligible public products without manual participant admission. Seller and management admission rules remain unchanged. Participant revocation still removes private-catalog access; it is not a ban on browsing public data. Revoked sessions, suspended accounts and service accounts cannot perform buyer actions. Only a buyer's own saved/cart/order data is returned.
- Existing catalog.public DTO names remain stable. Add set_public_listing(product_id, enabled, context). get_own_product includes public_listing. Existing get_demo_participant remains the adapter for authenticated buyer validation/serialization; get_demo_offer_snapshot still rechecks actual offer visibility and stock. It must not return private stock counts to browser DTOs.
- Cart lives inside demo_orders, not a second payment system. Only authenticated verified ordinary users can mutate it. URL names: cart (GET /cart/), cart-add (POST /cart/add/<uuid:variant_id>/), cart-update (POST /cart/items/<uuid:variant_id>/), cart-checkout (GET/POST /cart/checkout/). Lead integrates these routes. Disabled demo mode does not allow cart checkout/order creation and shows honest informational state.
- Cart data is persisted per account. Adding/changing/removing uses server-side Decimal validation and current offer checks, including fractional kg/m, whole pc, zero price, unavailable offers and self-purchase prohibition. No price/owner/trusted total from the browser. Order creation uses existing create_order in one atomic batch, stable intent identifiers and deterministic lock order. Repeated submission cannot double-reserve; a failed item cannot create a partial batch. Price changes between confirmation and submission require re-confirmation; never silently charge a changed total (even in simulation).
- Expose cart public functions get_cart(context), add_cart_item(variant_id, quantity, context), update_cart_item(variant_id, quantity, context), remove_cart_item(variant_id, context), checkout_cart(intent_id, context). get_cart has items, item_count, total, checkout_available and errors. A cart row includes variant_id, title, variant_label, seller_name, quantity, unit_label, unit_price, total, product_url, available and message. The confirmation token stores/validates the cart revision and expected current prices server-side.
- Keep existing demo-order lifecycle and owner checks; templates make history, payment simulation, cancellation and next actions readable. Group cart rows by seller without inventing a delivery cost. New public-source browsing is not proof of real trading readiness.
- Home template contract: storefront.categories (id/name/url/cover_id), storefront.items (existing search DTO plus url), storefront.total; populated from catalog.public with anonymous context. Empty installation shows an honest empty shop and owner-only setup directions, never fabricated merchandise.
- Provide an explicit idempotent demo-content command. It refuses to overwrite existing user data or open existing private products. Synthetic sellers/accounts are non-production and use unusable passwords; no fixed shared credentials. New content has public_listing=True intentionally. Bundle appropriately licensed source images with provenance and synthetic product descriptions. Normal migrations/startup do not seed automatically.

## Acceptance

1. Anonymous home/search/product/seller/photo browsing works only for opted-in eligible content; legacy private records, private offer contributions, unpublished photo references and inactive sellers remain undisclosed.
2. A verified ordinary buyer can browse, save, add two offers to cart, change quantity, remove, confirm a coherent total, create demo orders and see/cancel them. Duplicate checkout is idempotent; failures and changed price cannot partially succeed.
3. Seller can explicitly enable/disable public listing and manage their own content; no role is silently granted.
4. Demo catalog is reproducible from documented command, visually substantial, safely separable from private data, and its images work offline after installation.
5. Existing security/domain tests and added regression/browser tests pass. Both desktop and mobile renderings, forms, empty/error states, images, navigation and order transitions are exercised. Review rendered screenshots, not only selectors.
6. Clean Docker installation, backup/restore and source/secret audit pass; GitHub checks pass on the exact published commit. Archive is downloaded back and verified. Local demonstration switches only after backup and retains an executable rollback path.

Lead owns web/catalog_views.py public route integration/editor toggle, web/urls.py, config routes/settings, demo content/assets, docs, full verification, releases and local runtime. Do not edit another worker's files; notify the lead of integration needs.
